## Why a second registration

While preparing the first experiment, an audit of the held-out scripts and the library showed
that the harness as frozen could not have shown an effect even if the idea works:

1. Patterns were keyed by package: every function of a package shared the first pattern that
   package had produced, and retrieval fell back to loosely related patterns. A held-out
   script could receive an example for a different function, which is noise.
2. Base-R functions (`readLines`, `inherits`, `try`, ...) never became patterns, although
   they occur in most scripts and are the main thing that transfers across packages.
3. The endpoint, the score of the whole script, averages over many statements the library
   cannot inform, which dilutes any effect.

The harness was therefore changed (below), the primary endpoint was restricted to the entities
the library can inform, and the design was re-planned. This was done knowing the held-out
scripts' *structure* (their Stage-1 entities and which functions they call), but never
any translation score obtained on them under the experimental conditions (see "Prior contact
with the held-out set").

## Hypothesis

**H1 (primary).** For the fixed held-out set of scripts, the mean verification score over the
*targetable entities* (defined below) is higher when the library is fully trained than when it
is empty.

**Direction:** one-sided (library training increases scores). **H0:** no difference.

## What changed in the harness (all frozen at the hash above)

- **Function-keyed patterns.** One pattern per `(package, function)`. An assignment
  `x <- f(...)` is keyed by the function on the right-hand side. `c` and `list` key nothing.
- **Exact retrieval only.** A statement receives the pattern of its own key or nothing. The
  name-similarity fallback tier was built, evaluated and removed; it is not in the frozen code.
- **Nested base-R patterns.** For each script the library learns from, every base-R function
  called inside a statement gets a base-R pattern with the most focused verified example of
  it (fewest calls in the statement, then highest score). At translation time, the prompt lists
  such examples ("Base-R usage", at most 8) for the base functions the script calls.
- **Corrections.** When the agent rewrote a translation and the rewrite raised an entity's score,
  the (R snippet, corrected Python) pair is stored on the pattern of the functions involved and
  shown as "Verified fixes" (at most 5) when a later script calls them.
- **Examples are shown untruncated** (R snippet limit 1,000 characters, Python 2,000).
- Which base functions exist is taken from a fixed list of R 4.6.0 exports
  (`r2py/stage1/base_exports.json`, generated by `scripts/gen_base_exports.py`). Known
  limitation: a base name that a loaded package masks (`filter`, `lag`, `date`, ...) can be
  attributed to base R. Measured on the harvested corpus this affects 0.1% of entities (3 of 2,563).
- Unchanged: the verification layer, the scoring rubric and weights, the agent loop, the seeds
  (2 bare, 2 structured), score threshold 0.9, 20 iterations, 60 s script timeout.

## Design

### Held-out set
- **N = 60 scripts**, byte-identical to the list committed in `5e8eb2f` (the first
  registration's held-out set). Ten from each of six strata (`data_wrangling`, `date_time`,
  `graphics`, `html`, `stats_objects`, `other`), 55 packages. Strata are assigned by package
  (`STRATA` in `r2py/heldout.py`); string/text and file-I/O packages are inside `data_wrangling`.
- Never used for training. Every script's sha256 is in `experiments/heldout/manifest.json`
  and is verified before any run.

### Training set
- The pool is all scripts in `work/inputs/harvested` (3,988).
- **Package-quota draw:** for each package of the held-out set, up to **6** scripts (fewer if it
  has fewer spare), drawn at random (`random.Random("<seed>:train")`, seed 20260919) from the
  pool minus the held-out scripts, then interleaved across packages into one fixed order.
  Result: **256 scripts from 50 packages** (`manifest.json`, `train`).
- Five held-out packages have no other script in the pool and can never be covered by
  training: RColorBrewer, blob, cachem, conflicted, rematch.
- Consequence for interpretation: this tests whether the library helps on packages it has
  *seen*. It is not a test of transfer to unseen packages, except through base-R patterns.

### Training
- Library starts empty. Scripts are translated **one at a time, in the manifest order**, with the
  harness above and learning switched on. A script teaches the library only if its final
  score is >= 0.9 (entity patterns need an entity score >= 0.9). A training script that errors
  is retried once and then skipped.
- Training is sequential. Only scoring is parallelised.

### Checkpoints
Snapshots of the library after **0, 64, 128, 192 and 256** training scripts:
`empty`, `f1of4`, `half`, `f3of4`, `full`. Checkpoints are cumulative. Snapshots are
hash-verified before and after scoring.

### Repetitions
- Each held-out script is translated and scored **3 times per checkpoint** (independent runs),
  **60 x 3 x 5 = 900 scoring runs**. Scores are averaged over the 3 reps per script and
  checkpoint (and, for entities, per entity).
- A scoring run that errors is retried once. A run that still fails is recorded as failed and
  dropped from the means; the number of such runs is reported. Runs flagged as an infrastructure
  crash by the scorer are **not** excluded; their number is reported.

### Fixed conditions (training and scoring alike)
- Model `openrouter:google/gemma-4-31b-it`, **temperature 1.0**, provider pinned to
  `novita/bf16` with fallbacks disabled, request timeout 300 s. Applied by a wrapper around the
  API client (`pinned_llm`), so the harness hash is unaffected. Every scored row records the
  settings; `analyze` reports any mix. Rate-limit (429) responses are waited out with
  exponential backoff (5, 10, 20, 40 s) before the harness sees an error.
- Each scoring run gets a **throwaway copy** of its checkpoint's library and learning is off,
  so held-out scripts can never teach the library or each other.
- **Randomised order.** Per rep, scripts are shuffled and each script's checkpoints are
  shuffled (seed `20260919:score:<rep>`, recorded as `order_seed` on each row). A script's runs
  at different checkpoints therefore run at nearly the same time.
- **Parallel scoring.** Scoring uses 3 worker processes that take the next unclaimed run in
  that order. This only changes how long the experiment takes: runs share no state, and each
  writes to its own file. Training is not parallelised.
- Scoring starts after training has finished, so that all checkpoints are scored under the same
  model and the same installed R packages.

## Endpoints

**Targetable entity.** An entity of a held-out script (a statement in Stage-1's entity list)
is *targetable* if the **full** library holds a pattern **with a verified translation example**
for the entity's own key `(package, function)`, or for any base-R function called inside the
entity. The set of targetable patterns is read from the `full` checkpoint's files alone, never
from held-out scores. The single boilerplate entity `suppressPackageStartupMessages`, which
opens nearly every Rd example and which the model already gets right, is excluded from every
entity endpoint.

**Entity score.** Per entity, the entity-level verification score of the scorer (the
mean of its active effect dimensions, 0 if the entity failed to execute), averaged over reps.
Per script, the endpoint is the mean over the script's targetable entities that were scored
under **both** compared checkpoints.

### Primary analysis
For every held-out script that has at least one targetable entity scored under both `empty`
and `full`:

```
Δ = targetable_entity_mean(full) - targetable_entity_mean(empty)
```

**Test:** paired Wilcoxon signed-rank on the Δ values, `zero_method = "wilcox"` (tied pairs
are dropped; `n_nonzero` is reported), **one-sided (Δ > 0), α = 0.05**.
Also reported: two-sided p-value, mean and median Δ with SE, matched-pairs rank-biserial
correlation, counts of improved/tied/worse scripts, and Δ by stratum (descriptive).

The number of paired scripts (`n_paired`) and the share of scored entities that are targetable
are reported. Scripts without targetable entities are not part of this test, and no other
script is substituted. **No power calculation is claimed for this endpoint**: the number of
eligible scripts is unknown until the library is trained. (The power analysis in the first
registration applies to whole-script scores, not to this endpoint.)

### Control (descriptive, no test of record)
The same comparison for all *other* entities (those the library had nothing for). It is
expected to show no systematic change. A change of similar size there would point to a
non-specific cause (model drift, easier prompts) rather than the library, and would be
reported as such.

### Secondary analyses
1. **Whole-script score** (the first registration's endpoint): paired one-sided Wilcoxon,
   full vs empty, on the per-script mean over 3 reps, all 60 scripts, same reporting.
2. **Dose-response:** Page's trend test across the five ordered checkpoints, for the targetable
   endpoint (scripts with targetable entities under all five checkpoints) and for the
   whole-script score. Mean score per checkpoint and counts of monotone scripts are reported.

## What counts as a positive result
The primary hypothesis is supported if the paired one-sided Wilcoxon test on the targetable
entity mean, `full` vs `empty`, gives p < 0.05. Secondary and control results are reported
regardless of the primary result, and are not used to rescue or replace it.

## What counts as a negative or null result
If the primary test does not reject H0, this is reported as such: no other endpoint, subset of
scripts, checkpoint pair or test is promoted to headline after seeing the data. The
whole-script result is reported next to it in either case.

## Analysis is run once, after scoring is complete
`status` shows counts and running mean scores per checkpoint while scoring runs. These are for
operational monitoring. The experiment is not stopped, extended or altered based on them, only
for infrastructure failure (an API outage, a full disk, a provider change). `analyze` is run
after all 900 scoring runs have finished or been recorded as failed.

## Prior contact with the held-out set (disclosure)
- A Stage-1 audit ran on 59 of the 60 held-out scripts and 38 training scripts (entity kinds,
  which functions each calls, how many entities would be keyed). It involved no translation and
  no scores. It motivated the endpoint, the quota draw and the harness changes above.
- Before the first registration, an exploratory chronological analysis of 120 earlier runs
  (mean 0.72, SD 0.29) was done on ordinary translation runs. It is not part of this experiment.
- A dry run and a smoke test exercised the runner on a scratch manifest in a temporary
  directory. The smoke test scored two held-out scripts (`dplyr__rd_example__mutate_Rd.R`,
  `dplyr__rd_example__band_members_Rd.R`), 3 runs each, with a 4-script scratch library. All
  six scored 0.931; the library had nothing to say about either script (prompts identical).
  Its outputs are not part of the results and were not used to tune anything. The runs in this
  experiment are made from empty output directories.

## Known limitations, stated in advance
- Package coverage limits the effect: 5 of 55 held-out packages cannot be covered, and the
  effect is expected to concentrate in the packages the training sample covers.
- The result generalises to the domains and packages in the held-out set and to a library
  trained on 256 scripts, not to the whole corpus.
- The targetable endpoint is defined after the fact from the trained library. It cannot depend
  on held-out scores, but it depends on which entities the training happened to teach, so a
  per-run realisation of training matters. Training is run once; there is no estimate of
  its variance.
- Temperature 1.0 and only 3 repetitions leave translation noise. The 0.29 SD estimate was made
  under unpinned provider routing and may not hold under the pinned provider.
- Scripts that hit real network resources or R/Python environment differences can score
  identically at every checkpoint (floor or ceiling) and add ties.
- Attribution of base-R functions to entities depends on the frozen export list (see above).
- Run-time conditions (API load, time of day) differ between checkpoints only through the
  interleaved run order; they cannot be excluded entirely.

## Deviations from this plan
Any deviation (held-out set, training list, checkpoints, harness, endpoints, tests, LLM settings)
is logged in `experiments/heldout/DEVIATIONS.md` with a timestamp and rationale, committed
separately from this document, so this plan stays visible and unedited. A change to the harness
hash after registration invalidates the run and requires a new registration.
